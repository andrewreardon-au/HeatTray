# HeatTray

**v1.2** — 2026-10-09
**Author:** Andrew Reardon, andrewreardon@gmail.com

A standalone Windows system tray app that shows how much slower the CPU is
running than it normally can (a heat/power-limit slowdown indicator), as a
colour-coded number in the notification area. Built the same way as
`C:\ajr\PingTray` (single C# file, WinForms `NotifyIcon`, compiled with the
`csc.exe` bundled with .NET Framework — no SDK, no dependencies).

## Why it exists / the metric

Written after a long diagnosis session on a ThinkPad T14 Gen 5 (Ryzen 7 PRO
8840U) where the machine ran a sustained heavy VM load at ~96 °C.
Findings that shaped the design:

- **Windows' own throttle counters lie.** `Thermal Zone Information\%
  Passive Limit` and `Processor Information\% Performance Limit` stayed at
  100 / "no throttling" while HWiNFO showed the chip pinned at its
  sustained-power (STAPM) cap and ~99% of its thermal limit. Firmware limits
  are invisible to Windows.
- **HWiNFO's "Average Effective Clock" is a trap.** It averages in halted
  (idle) threads, so at 23% load it read ~890 MHz and made the machine look
  ~50% throttled. The Windows counter `Processor Information\% Processor
  Performance` is computed over *non-halted* time (APERF/MPERF), i.e. the
  speed of cores *while working*, and read ~3.4 GHz in the same window.
  That's the right "how fast am I really running" number, and it needs no
  third-party tool.
- So: the app measures the **outcome** (busy-core speed) against this
  machine's own normal speed at the same load (learned while not hot), plus
  the hottest ACPI thermal zone.
  It cannot say *why* it's slow (heat vs firmware power cap) — see README
  "Limits".

## How it works

- A WinForms `Timer` (default 2 s) calls `Sample()`, which reads three
  `System.Diagnostics.PerformanceCounter`s: `Processor Information` →
  `% Processor Performance` and `% Processor Time` (`_Total`; falls back
  to `Processor\% Processor Time`). **Not `% Processor Utility`**: it is
  scaled by clock speed (~ Time x Performance, verified with Get-Counter), so
  a hard throttle would drop a fully busy CPU under the idle gate and show a
  false "Idle" (found in adversarial review), and every instance of `Thermal Zone
  Information` → `Temperature` (Kelvin; the hottest zone wins, values outside
  200–500 K are ignored). Each counter needs one throw-away `NextValue()` at
  init because the first read is always 0.
- Perf and utility are smoothed over the last `SmoothN` (5) samples. Below
  `GateUtil` (30% load) the CPU is "idle": light-grey temperature number (or `-` with no thermal zone), speed not judged. A bare grey dash was unreadable in the tray, hence the number.
- **Per-load baseline (v1.1: robust percentile of cool samples).** Above the
  gate, the smoothed load picks one of `BucketCount` (5) bands of
  `BucketWidth` (15) %: gate..+15, +15..+30, ..., +60 and up. Each band keeps
  a histogram (`_hist[band][bin]`, 1%-wide bins of smoothed `% Processor
  Performance`, 0..250) fed **only by samples taken while the temperature is
  below `WarnC`** (unknown temperature counts as cool). The reference is the
  `RefPercentile` (75th) percentile of that histogram (`Reference()`); speed
  % = smoothed perf / reference, capped at 100. A band is "calibrated" after
  `CalibratedAfter` (30) cool loaded samples; until then the icon shows the
  temperature (grey, or alarm-coloured by temperature) and the tooltip says
  "Learning baseline" (or "Learning (needs cool)" when the band has no cool
  samples at all). Raw perf readings <=0 or >400 are skipped as glitches.
  Rationale: v1.0 used the all-time max per band and, within hours, the
  "best" ratcheted to 116% (boost while cool/light) so a normal 95% read as an
  18% slowdown at 75 C (a false alarm). A rolling percentile alone would let
  a long hot session wash out the cool reference; excluding hot samples from
  the histogram prevents that, and the percentile (not max) blunts boost
  bursts. `HistCap` (20000 samples, ~11 h of load) halves a band's counts so
  it can adapt to long-term change.
- **Colour** = worst of temperature (`WarnC` 85 → amber, `HotC` 92 → red) and
  calibrated speed (`AmberPct` 85, `RedPct` 70). No thermal zone → speed
  only.
- Baseline persists to `baseline.ini`: `version=2`, `gate=<N>`, then
  `b<N>=<bin>:<count>,<bin>:<count>,...` per band (sparse histogram). The file
  is discarded on load if the version isn't 2 (old best-ever format) or its
  gate differs from the one in force, since band edges move with the gate.
  Saved at most every 60 s when dirty, and on exit. Hot samples are never
  learned, so a hot first run can't poison it — but a band only ever seen hot
  stays "Learning (needs cool)". Users should still **Reset baseline...**
  (menu) when hardware or workload changes. Changing the idle gate in
  Settings resets the baseline too (band edges move with the gate).
- Text is drawn with a dark halo (8 offset draws) so it reads on both light and dark taskbars.
- Icon rendering, `DestroyIcon` handle cleanup, tooltip truncation
  (`NotifyIcon.Text` throws at ≥64 chars), the `-h`/`-v` console attach +
  Enter injection (`PrintOrShow`), the About dialog (not a MessageBox — no
  notification sound), and the settings.ini precedence rules (any CLI flag →
  settings.ini ignored, flags never persisted) are all deliberately the same
  as PingTray; see `C:\ajr\PingTray\CLAUDE.md` for the reasoning.
- Single instance per machine: named mutex `Global\HeatTray_SingleInstance`.
- `--diag` prints counter availability and 5 live 1-second samples then
  exits (works from a terminal or a pipe). Use it first when a colleague
  reports a grey `?`.

## Known limitations

- Counter names are English-only (`PerformanceCounter` category/counter
  names are localised on non-English Windows). Failure → grey `?`.
  `PdhAddEnglishCounter` would fix it but isn't wired up.
- ACPI thermal zone temperature has 1 K resolution and updates slowly, and
  reads a few °C off the CPU's Tctl (e.g. 90.3 vs 86.2 average in one
  window). Thresholds are therefore user-tunable.
- Cannot distinguish heat throttling from a firmware sustained-power cap,
  battery operation, or a Windows power mode - all read as "slow".
- Workloads within one load band differ (few busy cores boost higher than
  many at the same total load), so cool readings can wobble ~10%; the 75th
  percentile is a compromise. A band that has only ever been seen hot has no
  baseline ("Learning (needs cool)") rather than a wrong one.

## Trend, GHz and advice (added after v1.1, same version number)

- Tooltip when calibrated: `Speed 87% 2.9GHz ▼ | 91C | load 62% | Check cooling`. GHz = smoothed
  perf % x `~MHz` registry (nominal) clock. Arrow = `TrendDir()` (newest ~30 s vs oldest ~30 s of the last
  ~5 min of *loaded* samples, +/-3% threshold; hidden until ~2 min of load; ring cleared when idle).
- `AdviceShort()/AdviceLong()` encode the rule: speed >= AmberPct -> OK; slow+hot (>= WarnC) -> cooling;
  slow + under WarnC-5 -> power mode/AC/firmware cap; between -> heat or power cap.
- Colour deliberately stays = level (speed + temperature), NOT trend, so one colour never means two things.
- Details popup: Trend line, Advice line and a "HOW TO READ IT" section.

### Always-on speed display (icon + tooltip)
- Icon is **always the speed number** (temperature is no longer drawn on it). Judged (calibrated + loaded):
  % of the machine's own normal speed at that load, green/amber/red. Idle or learning: the raw busy-core
  speed as % of rated, Gainsboro (or amber/red by temperature) - not comparable to the judged number.
- Tooltip is always `Speed N% X.XGHz [arrow] | temp | load | tag`; tag = OK / Check cooling /
  Check power mode / Heat or power cap / Learning / Learning (hot) / Idle.
- GHz and % do not both fit in 16 px, so the menu has a checkable **Show GHz on icon** (settings.ini
  `icon=ghz|percent`; not persisted when CLI flags are in use, per the `_anyCli` rule).
- Arrows are written as C# ▲ escapes: the source has no BOM and csc would misread literal UTF-8.
  Keep the source ASCII.
- **Colour when judged = speed only** (green/amber/red from AmberPct/RedPct); temperature never recolours a
  judged icon (the aim is "is heat actually slowing me?"). Not judged (idle/learning): temperature colours it.
  `Severity()` is therefore only used for the unjudged case.
- Unjudged (idle/learning) icon is **always grey** now (no temperature colouring): an amber 104 next to
  a speed figure was misleading. `Severity()` is no longer used for the icon colour.

## v1.2 (2026-10-09) - SUPERSEDES the "per-load baseline / learning / bands" sections above

The learned per-band histogram baseline (v1.1) was removed as too fancy and unpredictable for a
user whose workload is a known, repeatable demo. Now:
- **One reference** from an explicit calibration: tray menu "Calibrate to demo load (5 min)..." (cool
  laptop, demo load running). Reference = **median of the last 40% of the window** (the settled speed;
  a cool start boosts for the first minutes, so a high percentile of the whole window would leave the
  demo permanently amber - found in adversarial review). Valid only with >= 40% of the readings a full
  window holds at the current interval (so intervals > 5 s still work). Stored in `baseline.ini`
  (`version=3`, `ref=`, `date=`, `maxtemp=`, `samples=`); older formats are ignored.
- Judged = loaded (>= gate) and a reference exists: speed% = smoothPerf / ref * 100 (NOT capped since the "one
  number" change below). Colour = speed only. Idle with a reference: same figure, green if >= AmberPct else grey
  (never orange/red). No reference: grey, GHz on the icon, tag "Idle" or "Needs calibration". (Superseded: the old
  rule was a cap at 100 and a grey raw-% icon for everything unjudged.)
- **Icon = one number by default** (see the "one number" section below): percent, GHz, or both (two lines, the old
  layout), drawn as `GraphicsPath` outlines scaled to fill a 32x32 bitmap (`RenderIcon`/`DrawFit`); calibrating still
  shows `CAL` over the countdown in cyan. (An older "Show GHz" toggle and its `icon=ghz` settings line are long gone;
  the new setting uses the key `show` precisely so a stale `icon=` line cannot flip anyone's icon.)
- `HotC`/`--hot` were removed in v1.2 (colour is speed only); old `hot=` lines in settings.ini are ignored. `WarnC` only drives advice and the "got hot during calibration" warning. Last calibration outcome is kept in Details (balloons can be
  suppressed by Focus Assist). Sleep/resume mid-calibration is not handled (wall-clock window).
- After a hardware / power-mode / AC-vs-battery / demo-load change: calibrate again.
- Details popup: `Row()`/`Para()` helpers wrap to `DetailsWidth` (82 chars) with a hanging indent; the box is 636 px wide.
  The trend ring only takes samples whose whole smoothing window is loaded (ramp-up from idle averaged in idle
  readings and showed a fake "+479% rising").
- Icon text fill: each of the two lines gets 14.5 of the 32 px (0.75 px margins); `DrawFit` fills the box
  HEIGHT and squeezes horizontally (never below 60%) only when the text is too wide, so "100" is as tall as
  "92". Verified over 130 strings that no glyph touches the canvas edge. The 16-24 px tray is the real limit:
  two lines cannot exceed ~7 px cap height at 100% scaling.
- "Clear reference..." menu item removed (recalibrating overwrites; delete baseline.ini to forget it).
- **Theme-aware icon colours.** `ApplyIcon` takes a `Tone` (Neutral/Good/Warn/Bad/Cal), not a `Color`;
  `ToneColor(tone, light)` maps it to a bright colour for a dark taskbar (Gainsboro/LimeGreen/Orange/Red/Cyan,
  dark halo) or a darker one for a light taskbar (35,35,35 / 0,130,0 / 205,100,0 / 200,0,0 / 0,120,170, white
  halo). `IsLightTaskbar()` reads `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\
  SystemUsesLightTheme` (the SYSTEM theme, not `AppsUseLightTheme`; dark when missing) on every redraw, so a
  theme switch shows within one sample (polling, because `SystemEvents` raises on its own thread). Before this,
  Gainsboro on a light taskbar was 1.4:1 contrast (GHz line and the grey idle number nearly invisible); now >= 3.5:1
  on #F3F3F3. `RenderIcon(top, bottom, topTone, bottomTone, light)` takes `light` explicitly as the test seam:
  do NOT flip the registry value to test (it changes the user's real desktop); render onto light backgrounds
  instead. `--diag` prints "Taskbar theme: light|dark". This dev machine is dark (SystemUsesLightTheme=0,
  ColorPrevalence=1 = maroon accent taskbar), so the light palette is only checked on rendered backgrounds.
- **"Judged" is internal jargon**: it means "speed compared with the calibrated reference" (loaded AND a
  reference exists). The user found "not judged" unclear, so all user-facing text (READMEs, Details, --diag)
  says what is actually happening instead: grey = "nothing to compare with" because the CPU is idle (it slows
  itself down on purpose) or there is no reference yet. Keep `judged` for identifiers/comments only.

  centre on a log scale over `ReckonPct`/`ReckonName`/`ReckonYear`. Anchor: the user's normal speed (100%) counts as
  a current laptop (3.0 GHz Zen 4 ~ 5 Skylake-GHz); each CPU estimated as clock x IPC vs Skylake. Specific models are
  used so the year is that model's debut (Pentium 60 = 1993, 486 DX2-66 = 1992), not the family's. **Every rung is an

  not judged or at/above AmberPct. Shown as tooltip line 4 and as the Details "Feels like:" row ("<cpu> from <year> -
  roughly Nx slower than normal"). "from" + year are joined with a no-break space `(char)0xA0` so any wrap falls before
  "from". Order-of-magnitude only; README documents the ladder.

  (`% Performance Limit` 100, `Throttle Reasons` 0, no Kernel-Processor-Power event 37). **Consequence: `AdviceShort()`
  (instant temperature) said "Check power mode" during the clamp, which was wrong (it is heat).** Fixed in the next
  section (the hint now looks back 2 minutes).
- Colour question raised by the user ("why is the percent red by the ghz grey"): the top line was coloured by the

  button name (`SystemTray.NormalButton`; this Windows 11 tray is XAML) and `CopyFromScreen` after
  `SetProcessDPIAware()` (without it a DPI-unaware PowerShell captures the wrong region on a scaled display).

## 9 Oct (later still): hint looks back 2 minutes; one colour on both icon lines

- **Hint accuracy fix** (user: "fix the hint accuracy"). `Sample()` calls `NoteTemp(_lastTempC)`, which keeps the last
  `HeatMemorySec` (120 s) of readings in `_tempRing` (`Queue<KeyValuePair<DateTime (UTC), double>>`; NaN is not stored;
  pruned by age). `HeatTempC()` = the hotter of now and the ring; it filters by age itself, so it does not depend on
  when the last prune ran. `HintFor(t)` is the old rule (NaN or < WarnC-5 -> power mode; >= WarnC -> cooling; else
  heat or power cap) and `AdviceShort()` = null / "OK" / `HintFor(HeatTempC())`. `PeakNote()` returns " (peaked 96C)"
  only when that hint differs from what the current temperature alone would give, so a calm "Check power mode" never
  carries a suffix. Tooltip line 3 = `AdviceShort() + PeakNote()`. Details: the `Temperature:` row adds "(hottest in
  the last 2 minutes: N C)" when that is >= 1 C above now; `Advice:` says "it was hot within the last 2 minutes
  (peak NC)"; a "Hints use:" row sits under HOW TO READ IT. Why 120 s: the real clamp held the CPU for 36+ s; a
  clamp that outlasts the window still reads "Check power mode" (stated in README Limits).
- **Both icon lines share one colour** (`ApplyIcon(.., tone, tone)`; CAL and its countdown are both Cyan).
- Verification: differential sweep (160 states, empty history) of the new build vs a build of HEAD = identical
  output; scenario table with synthetic history (pillow clamp, never hot, warm earlier, hot now, both window edges,
  expired peak, no sensor, OK speed); NoteTemp pruning and NaN handling; the real `Sample()` fills the ring; icon
  pixels show the top and bottom halves in the same colour for green/orange/red/grey/cyan. The new longest hint line
